# AGENTS.md

## Проект

**Արմատ** — небольшое статическое веб-приложение для изучения армянского языка.

Проект развивается как личный учебный инструмент: новые возможности и упражнения появляются по мере изучения языка и возникновения практической потребности в них.

Приложение работает без backend и базы данных. Сохраняйте реализацию простой и не добавляйте инфраструктуру, зависимости или абстракции без практической необходимости.

### Источник учебного материала

Если пользователь предоставляет материал для реализации урока — документ, текст, конспект, таблицу или другой источник — считайте этот материал каноническим источником содержания данного урока.

При реализации:

- сохраняйте смысл, правила, терминологию, примеры и границы темы исходного материала;
- не дополняйте и не изменяйте правило на основании учебников, интернета или собственных знаний без явного запроса пользователя;
- не заменяйте формулировку на более общую, полную или, по вашему мнению, более правильную, если это меняет содержание предоставленного урока;
- допускается адаптировать форму подачи для интерфейса: сокращать текст, разбивать его на блоки, добавлять упражнения и менять структуру представления, если учебный смысл остаётся неизменным;
- если в предоставленном материале обнаружена возможная ошибка, неоднозначность или противоречие с другим источником, не исправляйте её самостоятельно. Сообщите об этом пользователю отдельно и сохраните исходный материал до получения явного решения;
- внешние источники можно использовать для проверки или дополнительного контекста только тогда, когда пользователь явно этого просит. Они не должны незаметно становиться источником содержания урока.

## Контекст проекта

Для долговременного контекста проекта используются:

- `README.md` — публичное описание проекта;
- `AGENTS.md` — постоянные инструкции для Codex;
- `memory-bank/product.md` — долговременный контекст продукта и принятых решений.

Перед задачами, затрагивающими функциональность, UX, структуру контента, архитектуру или существенное поведение приложения, прочитайте `memory-bank/product.md`.

Для локальных технических изменений, не влияющих на продукт, загружать весь продуктовый контекст необязательно.

## Принципы разработки

- Предпочитайте простые решения, соответствующие текущему масштабу проекта.
- Не вводите новые библиотеки, framework, build system, backend или другие инфраструктурные компоненты без явной необходимости.
- Не создавайте абстракции заранее. Если несколько простых строк решают задачу лучше универсального механизма, предпочитайте простой вариант.
- Сохраняйте существующий визуальный стиль и UX, если задача явно не предполагает их изменение.
- Перед изменением существующего поведения определите, является ли оно намеренным продуктовым решением или случайной деталью реализации.
- Не превращайте текущее состояние реализации в постоянное ограничение без причины. Текущее количество уроков, упражнений, вариантов ответа и других сущностей само по себе не является инвариантом проекта.
- Не фиксируйте в документации информацию, которую проще и надёжнее получить непосредственно из кода или данных.

## Учебный контент и данные

Учебный контент является частью продукта, а не просто техническими данными.

При изменении букв, слов, упражнений или грамматических уроков:

- сохраняйте существующую структуру данных, если задача не требует её изменения;
- проверяйте согласованность правил, примеров, вопросов и правильных ответов;
- не изменяйте учебный смысл существующих материалов как побочный эффект технического рефакторинга;
- если структура данных изменяется, обновляйте связанные проверки одновременно с ней.

После изменений учебных данных обязательно запустите:

```bash
node scripts/check-data.mjs
```

## Проверка изменений

После реализации задачи:

1. Проверьте изменённое поведение приложения.
2. Запустите релевантные автоматические проверки.
3. Для изменений учебных данных обязательно выполните `node scripts/check-data.mjs`.
4. Просмотрите итоговый diff на случайные изменения, устаревшие комментарии и документацию.

### Разработка и сборка

- Используйте Node.js 24 (не ниже 24.12) и npm. Устанавливайте зависимости через `npm ci`, обновляйте lock-файл вместе с зависимостями.
- Исходники находятся в `src`, статические ресурсы — в `public`. `dist` генерируется сборкой: не редактируйте и не коммитьте её содержимое.
- Локальная разработка: `npm run dev`. Проверка готовой сборки: `npm run build` и `npm run preview`. Открытие через `file://` не поддерживается.
- TypeScript используется со строгой проверкой. Модули учебных данных импортируются и приложением, и проверочным скриптом Node; сохраняйте их совместимость с native type stripping: явные расширения `.ts`, `import type`, без runtime enum, JSX и браузерных зависимостей.
- После изменения интерфейса, маршрутов или тренировок выполняйте `npm run typecheck`, `node scripts/check-data.mjs`, `npm test`, `npm run build` и `npm run test:e2e`. Для первого запуска браузерных тестов установите Chromium через `npx playwright install chromium`.
- Браузерные тесты используют собранное приложение через локальный preview. После изменения исходников перед ними необходима новая сборка. Сам `vite preview` не является production-сервером.

### CI и публикация

CI проверяет изменения после push и в pull request, собирает приложение и сохраняет сборку как артефакт. CI не публикует приложение. Не включайте deployment без задачи на публикацию.

Требования к хостингу: раздавать содержимое `dist` из корня домена и возвращать `index.html` для маршрутов приложения. Отсутствующие статические ресурсы должны получать 404. Backend и постоянно работающий Node.js для раздачи сборки не требуются.

## Документация проекта

`README.md`, `AGENTS.md` и `memory-bank/product.md` имеют разные назначения и должны оставаться согласованными между собой.

### Ответственность файлов

#### `README.md`

Публичное описание проекта для человека, впервые открывшего репозиторий.

README должен содержать только информацию, полезную пользователю или посетителю репозитория:

- что представляет собой Արմատ;
- зачем существует проект;
- его основные возможности;
- как открыть опубликованное приложение;
- минимальную общую информацию о проекте.

Не используйте README как техническую документацию, описание внутреннего формата данных или инструкцию для Codex.

#### `AGENTS.md`

Постоянные инструкции для Codex.

Здесь должны находиться:

- правила разработки;
- устойчивые технические ограничения;
- conventions;
- обязательные проверки;
- правила работы с документацией и контекстом проекта.

Не храните здесь подробное описание текущего состояния продукта, если оно не является постоянным ограничением или правилом разработки.

#### `memory-bank/product.md`

Долговременная память о продукте.

Здесь должны находиться:

- назначение продукта;
- текущее существенное поведение и возможности;
- важные UX-решения;
- структура продукта и контента, если она важна для будущей разработки;
- существенные архитектурные и технические решения;
- причины нетривиальных решений;
- принятые направления развития или осознанно отвергнутые подходы, если это важно для будущих итераций.

`product.md` должен описывать текущее актуальное состояние и контекст, а не быть журналом истории изменений.

### Канонический владелец информации

У каждой информации должен быть один основной владелец.

Не дублируйте одинаковые сведения между `README.md`, `AGENTS.md` и `memory-bank/product.md` только для удобства.

Допустима краткая ссылка или необходимое пересечение контекста, но при изменении информации должно быть понятно, какой файл является её каноническим источником.

## Поддержание актуальности документации

Поддержание документации является частью выполнения задачи и не требует отдельного запроса пользователя.

Перед завершением **каждой задачи** проверьте, появилось ли новое долговременное знание или стала ли существующая документация неточной.

Если да, обновите соответствующий файл в рамках той же задачи:

- `README.md` — если изменилось публичное назначение проекта или его основные пользовательские возможности;
- `memory-bank/product.md` — если изменились возможности продукта, UX, структура контента, архитектура или было принято существенное продуктовое или техническое решение;
- `AGENTS.md` — если появилось или изменилось постоянное правило разработки, ограничение, convention, обязательная проверка или другая инструкция, которую должны учитывать будущие сессии Codex.

Если новое решение заменяет старое, измените или удалите устаревшее описание вместо накопления противоречащих друг другу состояний.

При изменении одного из этих файлов проверьте, не возникло ли противоречие с двумя другими.

Не добавляйте в долговременную документацию:

- временные детали текущей задачи;
- промежуточные состояния реализации;
- значения и количество сущностей, которые легко определить из кода;
- подробную инструкцию по реализации одной конкретной фичи;
- решения и планы, которые ещё не были приняты;
- информацию, уже имеющую другого канонического владельца.

## Критерий завершения задачи

Задача считается завершённой, когда:

- требуемое поведение реализовано;
- релевантные проверки выполнены;
- итоговый diff проверен на случайные изменения;
- `README.md`, `AGENTS.md` и `memory-bank/product.md` проверены на актуальность и согласованность;
- необходимые изменения документации внесены в рамках той же задачи.
