# AGENTS.md

## Проект

**Արմատ** — небольшое статическое веб-приложение для изучения армянского языка.

Проект развивается как личный учебный инструмент. Новые возможности, уроки и упражнения появляются по мере изучения языка и возникновения реальной практической потребности.

Приложение работает без backend и базы данных. Сохраняйте реализацию простой: не добавляйте инфраструктуру, зависимости, уровни абстракции или универсальные механизмы без практической необходимости.

## Источник учебного материала

Если пользователь предоставляет материал для реализации урока — документ, текст, конспект, таблицу или другой источник — считайте его каноническим источником содержания этого урока.

При работе с таким материалом:

- сохраняйте смысл, правила, терминологию, примеры и границы темы исходного материала;
- не дополняйте и не изменяйте правила на основании учебников, интернета или собственных знаний без явного запроса пользователя;
- не заменяйте формулировки на более общие, полные или, по вашему мнению, более правильные, если это меняет содержание предоставленного урока;
- разрешается адаптировать форму подачи для интерфейса: сокращать текст, делить его на смысловые блоки, добавлять упражнения и менять структуру представления, если учебный смысл сохраняется;
- если в материале обнаружена возможная ошибка, неоднозначность или противоречие, не исправляйте её самостоятельно. Отдельно сообщите об этом пользователю и до его решения сохраняйте исходный вариант;
- используйте внешние источники для учебного содержания только по явному запросу пользователя. Они не должны незаметно становиться источником правил или примеров урока.

## Контекст проекта

Для долговременного контекста используются три документа:

- `README.md` — публичное описание проекта;
- `AGENTS.md` — постоянные инструкции для Codex и технические правила работы с проектом;
- `memory-bank/product.md` — долговременный продуктовый контекст и принятые продуктовые решения.

Перед задачами, которые затрагивают функциональность, UX, структуру учебного контента или существенное пользовательское поведение, прочитайте `memory-bank/product.md`.

Для локальных технических изменений, которые не влияют на продукт, полностью загружать продуктовый контекст необязательно.

## Принципы разработки

- Предпочитайте простые решения, соответствующие текущему масштабу проекта.
- Не вводите новые библиотеки, framework, build system, backend или другие инфраструктурные компоненты без практической необходимости.
- Не создавайте абстракции заранее. Если несколько простых строк решают задачу лучше универсального механизма, используйте простой вариант.
- Сохраняйте существующий визуальный стиль и UX, если задача явно не требует их изменения.
- Перед изменением существующего поведения определите, является ли оно намеренным продуктовым решением или случайной деталью текущей реализации.
- Не превращайте текущее состояние кода в постоянное ограничение без причины. Количество уроков, упражнений, вариантов ответа и других сущностей само по себе не является инвариантом проекта.
- Не переносите в долговременную документацию сведения, которые проще и надёжнее получить непосредственно из кода или данных.

## Учебный контент и данные

Учебный контент является частью продукта, а не просто техническими данными.

При изменении букв, слов, упражнений или грамматических уроков:

- сохраняйте текущую структуру данных, если задача не требует её изменения;
- проверяйте согласованность правил, объяснений, примеров, вопросов и правильных ответов;
- не меняйте учебный смысл существующего материала как побочный эффект технического рефакторинга;
- при изменении структуры учебных данных одновременно обновляйте связанные проверки;
- не дублируйте одни и те же учебные данные без необходимости. Если один пример, форма или другой материал используется в нескольких местах, предпочитайте один канонический источник, чтобы объяснение и упражнения не могли незаметно разойтись.

После изменения учебных данных обязательно выполните:

```bash
node scripts/check-data.mjs
```

## Проверка изменений

После реализации задачи:

1. Проверьте изменённое поведение приложения.
2. Запустите релевантные автоматические проверки.
3. После изменения учебных данных обязательно выполните `node scripts/check-data.mjs`.
4. Просмотрите итоговый diff и убедитесь, что в нём нет случайных изменений, устаревших комментариев или ставшей неточной документации.

### Разработка и сборка

- Используйте Node.js 24, не ниже 24.12, и npm.
- Для установки зависимостей используйте `npm ci`.
- При изменении зависимостей обновляйте lock-файл вместе с ними.
- Исходный код находится в `src`, статические ресурсы — в `public`.
- `dist` является результатом сборки. Не редактируйте и не коммитьте его содержимое.
- Для локальной разработки используйте `npm run dev`.
- Для проверки production-сборки используйте `npm run build` и `npm run preview`.
- Открытие приложения непосредственно через `file://` не поддерживается.
- TypeScript используется в строгом режиме.
- Модули учебных данных используются как приложением, так и Node.js-скриптами. Сохраняйте их совместимость с native type stripping: используйте явные расширения `.ts`, `import type`, не добавляйте runtime enum, JSX или браузерные зависимости в такие модули.
- После изменений интерфейса, маршрутов или тренировок выполняйте:

```bash
npm run typecheck
node scripts/check-data.mjs
npm test
npm run build
npm run test:e2e
```

Для первого запуска браузерных тестов при необходимости установите Chromium:

```bash
npx playwright install chromium
```

Браузерные тесты работают с собранным приложением через локальный preview, поэтому после изменения исходников перед их запуском необходима актуальная сборка.

`vite preview` используется только для проверки сборки и не является production-сервером.

### CI и публикация

CI проверяет изменения после push и в pull request, выполняет необходимые проверки, собирает приложение и сохраняет сборку как артефакт.

CI не публикует приложение автоматически. Не добавляйте deployment без отдельной задачи на изменение процесса публикации.

Production-хостинг должен:

- раздавать содержимое `dist` из корня домена;
- возвращать `index.html` для клиентских маршрутов приложения;
- возвращать 404 для отсутствующих статических ресурсов.

Для работы опубликованного приложения не требуются backend или постоянно запущенный Node.js-процесс.

## Документация проекта

`README.md`, `AGENTS.md` и `memory-bank/product.md` имеют разные назначения. Они должны быть согласованы, но не должны дублировать друг друга без необходимости.

### Ответственность файлов

#### `README.md`

Публичное описание проекта для человека, впервые открывшего репозиторий.

README должен кратко объяснять:

- что представляет собой Արմատ;
- зачем существует проект;
- какие основные возможности доступны пользователю;
- где открыть опубликованное приложение;
- минимальную общую информацию, полезную посетителю репозитория.

Не используйте README как подробную техническую документацию, описание внутреннего устройства данных или инструкцию для Codex.

#### `AGENTS.md`

Постоянные инструкции для Codex и канонический источник устойчивых технических правил проекта.

Здесь должны находиться:

- правила разработки;
- существенные технические ограничения;
- архитектурные правила, которые необходимо учитывать при будущих изменениях;
- используемые conventions;
- требования к структуре проекта, если они являются устойчивым правилом;
- правила сборки, тестирования, CI и публикации;
- обязательные проверки;
- правила работы с учебными данными;
- правила ведения документации и продуктового контекста.

Не превращайте `AGENTS.md` в полный пересказ текущего кода. Информацию, которую легко и однозначно определить из реализации и которая не является постоянным правилом, документировать здесь не нужно.

#### `memory-bank/product.md`

Долговременная память о продукте.

Здесь должны находиться:

- назначение продукта;
- существенные пользовательские возможности;
- наблюдаемое пользователем поведение;
- важные UX-решения;
- структура продукта и учебного контента, если она важна для дальнейшего развития;
- продуктовые ограничения и инварианты;
- причины нетривиальных продуктовых решений;
- принятые направления развития или осознанно отвергнутые продуктовые подходы, если это важно для будущих итераций.

Не описывайте в `product.md` способ технической реализации сам по себе: framework, библиотеки, build system, router, внутреннюю структуру исходников, формат хранения данных, CI, hosting и другие implementation details.

Если техническое решение важно потому, что оно определяет наблюдаемое поведение продукта, в `product.md` фиксируйте именно пользовательское поведение или продуктовое ограничение. Сам способ реализации при необходимости документируйте в `AGENTS.md`.

Например:

- `Каждый урок и блок можно открыть по прямой ссылке` — продуктовый контекст;
- `Маршрутизация реализована через BrowserRouter` — техническая реализация.

`product.md` описывает актуальное состояние продукта и контекст принятых решений. Он не является журналом изменений.

### Канонический владелец информации

У каждого долговременного знания должен быть один основной владелец.

Не копируйте одинаковое описание в `README.md`, `AGENTS.md` и `memory-bank/product.md` только ради удобства.

Допустимо краткое необходимое пересечение контекста, однако при изменении информации должно быть понятно, какой документ является её каноническим источником.

## Поддержание актуальности документации

Проверка документации является частью выполнения задачи и не требует отдельного запроса пользователя.

Перед завершением каждой задачи определите:

- появилось ли новое долговременное знание;
- изменилось ли существующее продуктовое решение;
- изменилось ли постоянное техническое правило;
- стала ли какая-либо существующая документация неточной.

Если да, обновите соответствующий файл в рамках той же задачи:

- `README.md` — если изменилось публичное назначение проекта или его основные пользовательские возможности;
- `memory-bank/product.md` — если изменились пользовательские возможности, UX, структура продукта или учебного контента, продуктовое ограничение, существенное пользовательское поведение либо было принято важное продуктовое решение;
- `AGENTS.md` — если изменилась архитектура, технологический стек, постоянное техническое ограничение, convention, структура проекта, процесс сборки или публикации, обязательная проверка либо другая инструкция, которую должны учитывать будущие сессии Codex.

Чисто технический рефакторинг не является причиной изменять `product.md`, если пользовательское поведение и продуктовые решения остались прежними.

Если новое решение заменяет старое, измените или удалите устаревшее описание. Не накапливайте в документации последовательные или противоречащие друг другу исторические состояния.

После изменения одного из трёх документов проверьте, не возникло ли противоречие с двумя другими.

Не добавляйте в долговременную документацию:

- временные детали текущей задачи;
- промежуточные состояния реализации;
- значения и количество сущностей, которые легко получить из кода или данных;
- подробные инструкции по реализации одной конкретной функции;
- решения и планы, которые ещё не были приняты;
- информацию, уже имеющую другого канонического владельца.

## Критерий завершения задачи

Задача считается завершённой, когда:

- требуемое поведение реализовано;
- релевантные проверки выполнены;
- итоговый diff проверен на случайные изменения;
- `README.md`, `AGENTS.md` и `memory-bank/product.md` проверены на актуальность и согласованность;
- необходимые изменения документации внесены в рамках той же задачи.
